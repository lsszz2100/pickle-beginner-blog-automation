# 09-2. 상태 파일과 재개

## 상태 파일이 없으면 생기는 일

자동 발행을 사흘 돌리면 반드시 한 번은 멈춥니다. 그때 상태를 남기지 않았으면, 처음부터 다시 하거나, 어디까지 했는지 눈으로 확인해야 합니다. 하루 마흔 편이면 이 확인에 한 시간이 걸립니다.

상태 파일은 그 한 시간을 없애는 장치입니다. 남길 것은 세 가지입니다.

1. 마지막으로 성공한 항목
2. 다음에 할 항목
3. 실패한 항목과 이유

## 파일 구조

```json
{
  "date": "2026-11-26",
  "batch": "2026-11-26-A",
  "done": ["01", "02", "03"],
  "failed": [{"item": "04", "reason": "이미지 3장 미만", "at": "07:22"}],
  "last_slot": "2026-11-26T21:40:00+09:00",
  "slugs": ["python-work-automation-5-examples", "tsmc-2nm-future"]
}
```text

`done`과 `failed`를 나눕니다. 실패는 다시 시도하고, 완료는 건너뜁니다. 하나로 합치면 재시도할 것과 아닌 것이 섞입니다.

## 재개 방법

```python
def pending(state, items):
    done = set(state["done"])
    return [i for i in items if i["nn"] not in done]
```text

실행 전에 이 함수로 남은 항목만 고릅니다. 재실행이 안전하면 작업을 작게 나눌 수 있고, 작게 나누면 실패의 영향이 줄어듭니다.

## 로그를 사람이 읽을 수 있게

```text
[07:15] batch 2026-11-26-A
[07:15] 01 ok  (3,842자, 태그 10, 이미지 5)
[07:16] 02 ok  (4,105자, 태그 10, 이미지 4)
[07:18] 03 skip (이미 존재: python-work-automation-5-examples)
[07:19] 04 fail (이미지 2장)
[07:19] 중단: 실패 1건
```text

한 줄에 결과와 근거를 함께 적습니다. "ok"만 있으면 나중에 검증할 수 없고, "fail"만 있으면 무엇이 문제였는지 알 수 없습니다.

## 상태 파일을 어디에 두는가

| 위치 | 장점 | 단점 |
| --- | --- | --- |
| 로컬 파일 | 빠름, 단순 | 기기마다 다름 |
| 저장소 | 이력 남음 | 민감정보 위험 |
| 클라우드 문서 | 어디서나 확인 | 동기화 지연 |

이 책은 로컬 파일을 기준으로 합니다. 저장소에 올릴 때는 계정 정보가 없는지 확인합니다. 상태 파일에는 슬러그와 시각만 있고, 토큰이나 비밀번호는 없어야 합니다.

## 실패 항목을 다시 돌리는 기준

| 이유 | 재시도 |
| --- | --- |
| 이미지 부족 | 원고 보강 후 |
| 글자 수 미달 | 원고 보강 후 |
| 사이트 오류 | 다음 회차 |
| 중복 슬러그 | 재시도하지 않음 |
| 인증 실패 | 설정 확인 후 |

중복은 재시도해도 결과가 같습니다. 원고 문제는 원고를 고쳐야 합니다. 사이트 오류만 시간이 해결합니다. 이 구분이 없으면 실패한 항목을 영원히 다시 돌립니다.

## 한 달 뒤 상태 파일 정리

상태 파일은 날짜별로 쌓입니다. 한 달이 지나면 오래된 파일을 압축해 보관합니다. 지우지는 않습니다. 같은 주제를 다시 쓰지 않기 위한 기록이기 때문입니다. 압축한 파일에서 제목만 뽑아 목록으로 만들어 두면, 새 주제를 고를 때 검색 한 번으로 중복을 확인할 수 있습니다.
